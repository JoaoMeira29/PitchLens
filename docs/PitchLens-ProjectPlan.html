Assumptions behind this plan. Two engineers with roughly 6–10 hours a week each, about 16 weeks to a polished launch, Python for data work, a budget close to zero, and a public, non-commercial project. If any of these is off (more time, a specific league you care about, a commercial ambition), the scope and data choices shift; the sections on data and roadmap say where.

Six project ideas, compared

Each one is buildable with free data. They differ in how much football analysis you'd actually learn, how well they'd read to a recruiter, and how likely they are to blow up in scope.

The recommendation: PitchLens

PitchLens is a public web app and a set of written analyses built on one idea: show the numbers and show the method. Every match page explains itself, the xG model is your own and benchmarked in the open, and the weekly forecast publishes its own track record, including the weeks it gets wrong.

It's layered on purpose. The core runs on static historical data, so it can never break because an API changed. A thin live layer gives you a real scheduled pipeline to operate. The AI layer sits on top and only ever describes numbers you computed yourselves.

The problem

Most public football stats show numbers without methods, and open advanced data got scarcer in January 2026 when FBref had to delete its Opta-powered advanced stats. Learners and fans have few places where the model, the code and its errors are all visible.

Who it's for

First, the two of you, as a structured way to learn. Second, curious fans and amateur writers who want readable match visuals. Third, recruiters and analysts scanning your portfolio. Be honest that the third group matters most.

Why it's interesting

You'll disagree with a professional xG model and have to explain why. Your forecasts will be scored publicly. Those two moments of accountability make far better portfolio stories than another dashboard.

Free football data is narrower than it looks, and licensing matters more for a public project than for a private notebook. Prefer sources that explicitly permit your use; avoid scraping sites whose terms forbid it.

Architecture

Batch everything. Football data changes a few times a week, so there is no need for streaming, queues or per-request computation. Heavy work happens in the pipeline; the API only reads precomputed tables; the frontend only draws.

Pipeline

A Python package with a small CLI (ingest, validate, train, publish). Idempotent: rerunning never duplicates data. Raw files are cached so you never re-download history.

Storage

Parquet and DuckDB for analysis on your laptops and in CI. Postgres only for the small set of tables the website needs.

Backend

FastAPI, read-only endpoints such as /matches/{id}/shots. Typed with Pydantic, which gives you an OpenAPI spec the frontend can generate types from.

Frontend and deploy

Static React build on Vercel. API as one Docker container on Google Cloud Run, scaling to zero. Running cost: about €0 a month plus a few euros of AI usage.

Deployment that fits a side project

Frontend on Vercel, API as a Docker container on Google Cloud Run, Postgres on Supabase, scheduling in GitHub Actions. Every piece has a free tier that fits a portfolio, and the API scales to zero so an idle site costs nothing. The technologies section covers the setup, costs and catches in detail.

Plan for the end, too. Before you move on to other things, add an "archive mode": export the serving tables to static JSON so the site keeps working on static hosting with no database, no API and no bills. A portfolio link that 404s in two years undoes all the work.

Where AI helps, and where it shouldn't touch the numbers

The rule is simple: conventional methods produce every number; language models only describe numbers that already exist. Language models are fluent and confidently wrong about statistics, and a sports analytics portfolio lives or dies on getting numbers right.

AI adds genuine value

  • Match notes. Feed the model a JSON of computed stats for one match; ask for 80 words. Generate offline in the pipeline, store the result, and never call the model on a page view. That keeps costs to a few euros and lets you review output.
  • Explaining charts to beginners. Short "how to read this" text for each chart type, written once with AI help and edited by you.
  • Your own learning. Asking an assistant why your calibration curve bends, or what a feature leak looks like, is one of the fastest ways to learn analytics.
  • Building faster. Scaffolding, tests, CI configs and refactors with a coding agent.

Conventional analysis is more reliable

  • xG and any probability. Logistic regression and gradient boosting are transparent, calibratable and testable.
  • Forecasts. Poisson models and Elo ratings are the honest baselines; an LLM "predicting" a score is a coin flip in a suit.
  • Rankings and comparisons. Percentiles and per-90 numbers must be computed, never generated.
  • Data cleaning. Deterministic code with tests. Ambiguous cases get a rule, not a guess.

Making AI output trustworthy

Write a faithfulness test: extract every number from a generated note and assert each one appears in (or is directly derivable from) the input JSON. Ask the model for structured output with the claims it makes, so the check is easy. Notes that fail are regenerated or dropped, and each published note is labelled as AI-written. This single test is a better portfolio talking point than most AI features.

"Ask the data in plain English" (text-to-SQL) is tempting. Treat it as an optional experiment, run against a read-only database role, and only after everything else works.

Getting player data from your own match video

Yes, you can, and it fits the name: this is the "lens" in PitchLens. Computer vision can turn match footage into per-player positions and movement. What it can't do cheaply is produce a full StatsBomb-style event log. Knowing that difference up front keeps the scope sane.

What you want per player How hard from video Realistic?
Position over time, heatmap Detect players each frame, track them across frames, map pixels to pitch coordinates using the pitch lines. Yes
Distance covered, speed, sprints Falls out of the positions once the pitch mapping is good. Errors grow with distance from the camera. Yes
Team shape and average positions Split players into teams by shirt colour (simple clustering), then average positions per phase. Yes
Who is who (names) Reading shirt numbers is unreliable at amateur resolution. Easiest fix: a person assigns names to track IDs in a small review screen. With help
Ball position Small, fast and often hidden. Expect gaps you interpolate or fill by hand. Partly
Passes, shots, tackles per player Needs reliable ball tracking plus action recognition. A research problem; semi-manual tagging is the honest route. Not yet

The footage matters more than the model

Film your own games, or a local club's with permission, from a single fixed, elevated, wide camera that sees most of the pitch: a tripod on a stand, or a panoramic sports camera. TV broadcasts are much harder (zooms, camera cuts, replays) and copyrighted, so you can't publish data or clips derived from them. Your own footage is clean legally and technically. If other people appear, get their consent before publishing anything, and consider showing initials or anonymised IDs.

How the pipeline would look

Frames go through a player detector (a YOLO-family model, fine-tuned on a few hundred labelled frames from your camera), a multi-object tracker such as ByteTrack, a pitch keypoint model or manually clicked corner points to compute a homography, then team assignment by shirt colour. The output is a table of frame, track_id, team, x, y in the same pitch coordinates as the rest of PitchLens, so your existing charts and metrics work on it unchanged. Open-source examples (Roboflow's sports repository, the SoccerNet research datasets) are good starting points.

Compute and scope

This needs a GPU. Process videos offline as a batch job on a free notebook GPU or a rented one, never inside your web API. Start with a 5-minute clip, not a full match. Measure accuracy honestly by hand-labelling 100 frames and reporting error in metres; that evaluation is what makes it a portfolio piece rather than a demo.

Where it goes in the roadmap: after launch, as phase 7 (about 4–6 weeks). It's the most impressive AI feature in the project and the one most likely to swallow everything else, so it waits until the core is public. A good first milestone: upload a clip of your own 7-a-side game and get a heatmap and distance covered for every player.

Docker: where it earns its place

Use Docker for

  • The API image. It's the deploy unit for Cloud Run, and the exact same image runs locally and in CI.
  • Local Postgres. Compose gives both of you an identical database in one command.
  • CI test database. A Postgres service container in GitHub Actions for API tests.
  • The video lab, later. A CUDA-based image so the GPU job runs the same on any rented machine.

Skip Docker for

  • The frontend. Vercel builds and serves the static files itself.
  • The pipeline and notebooks. uv already gives reproducible environments; a container adds friction to exploration.
  • Orchestration. No Kubernetes, no Swarm. One container, one service.

Connecting frontend and API. Add a rewrite in vercel.json that sends /api/* to the Cloud Run URL. The browser only ever talks to one origin, so there's no CORS setup, and you can move the API later without touching frontend code. Because data changes at most twice a week, send Cache-Control headers from the API generously.

Secrets, and where each one lives. FOOTBALL_DATA_TOKEN, ANTHROPIC_API_KEY and the writer DATABASE_URL exist only as GitHub Actions secrets, because only the pipeline needs them. Cloud Run gets a separate, read-only database role. GitHub authenticates to Google Cloud with Workload Identity Federation, so there's no long-lived JSON key to leak. Nothing secret ever reaches the frontend, and the browser never talks to Supabase directly.

Meaningful tests and GitHub Actions

The tests that matter in sports analytics are the ones that catch silently wrong numbers. A broken page is obvious; a flipped coordinate axis that puts every shot on the wrong wing can survive for months.

Layer What to test Tools
Transforms Coordinate conversion (StatsBomb pitches are 120 × 80 with the origin top-left), shot angle and distance against hand-calculated cases, own goals and penalties handled correctly, extra time not double-counted. pytest with small, named example cases
Invariants xG always between 0 and 1; forecast probabilities for home, draw and away sum to 1; team totals equal the sum of player totals. Hypothesis (property-based tests)
Data contracts Every staged table has the expected columns, types, ranges and no duplicate event IDs. Fails loudly when a source changes format. pandera schemas
Pipeline end to end Run ingest-to-publish on the two committed fixture matches and compare outputs with a snapshot. pytest + snapshot files
Model quality Train on a fixed sample with a fixed seed; fail if log loss gets worse than the recorded baseline by more than a small tolerance. Catches accidental feature leaks and regressions. pytest, metrics stored in repo
API Status codes, response schemas, 404s for unknown matches, query performance on indexed columns. pytest + httpx TestClient, test Postgres in Docker
Frontend Pitch scaling functions, chart components rendering given data, and one smoke test that loads a match page. Vitest, Testing Library, Playwright
AI notes Faithfulness check on every generated note; prompt changes run against a small set of stored example matches. pytest with a mocked client in CI

Three workflows are enough

ci.yml runs on every pull request: lint and type-check both apps, run the Python and frontend tests, build the Docker image, and fail if the generated TypeScript API types are out of date with the backend. deploy.yml runs on merge to main: push the image, deploy the API, let the static host build the frontend, then run the Playwright smoke test against production. forecast.yml runs on a schedule after each round of matches. Add Dependabot for dependency updates and require one review per pull request, which also forces the two of you to read each other's code. 

# .github/workflows/forecast.yml
name: weekly-forecast
on:
  schedule:
    - cron: "0 6 * * 2,5"   # Tue and Fri 06:00 UTC, after weekend and midweek rounds
  workflow_dispatch:            # manual re-run button
jobs:
  forecast:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

        env: { DATABASE_URL: ${{ secrets.DATABASE_URL }} }

Dividing the work between two people

Divide work by task lead, not by silo. Every issue has one lead and one pairing/review partner; switch leads on crossovers so both of you build and review data, models, API, frontend, tests, and delivery. Both of you approve phase exits and anything published.

Working rhythm

Agree the API contract first (OpenAPI spec plus example JSON), so the frontend can be built against mock data while the pipeline catches up. Keep a GitHub Projects board with small issues. Hold one 30-minute call a week to demo what changed and pick next week's issues; do everything else asynchronously in pull requests. Give every issue one lead and one reviewer, and alternate who leads cross-discipline tasks. Pair on coordinate systems, model evaluation, API contracts, and the AI faithfulness test. Record decisions as short ADRs in docs/, which doubles as evidence of engineering judgement.

Presenting it in your portfolios

Analytics hiring managers read your thinking more than your code. Give them both, and make your limitations visible: admitting what your model misses reads as competence.

The shared project

A README that opens with a 20-second GIF, the live link and a one-paragraph pitch, followed by the architecture diagram, how to run it, data attribution and a "what we learned" section. A methods page and model cards on the site itself. A 90-second demo video walking through one match.

Two or three written analyses

These carry more weight than the app. Good candidates: "We built an xG model and compared it with a professional one: here's where we disagree and why"; "Scoring our league forecasts after ten rounds"; "What 360 data changes about chance quality". Publish on a blog or the site's own notes section, share charts with StatsBomb attribution, and post in the football analytics community, where open work gets noticed.

Your individual case studies

Each of you writes a short "my role" page: the problem you owned, two or three decisions with trade-offs, links to your key pull requests, and one thing you'd do differently. On a CV, be specific: "Built and benchmarked an expected-goals model (logistic regression, 360 features) on 3,000+ shots; published methodology and calibration analysis" beats "Worked on a football analytics app". Later, research competitions such as Hudl's annual Performance Insights call are a natural next step for the strongest analysis.

Analytics glossary for the first month

The handful of terms you'll meet on day one, in plain words.

Event data
A log of on-ball actions (pass, shot, tackle) with time, location and players. What StatsBomb open data contains.
Tracking data
Positions of all 22 players and the ball many times per second. Rare and expensive; a few public samples exist.
xG (expected goals)
The probability a shot becomes a goal, estimated from similar past shots. A penalty is about 0.76–0.79; a shot from 30 metres is about 0.02–0.04.
Per 90
A stat scaled to a full match, so players with different minutes compare fairly. Unreliable below roughly 900 minutes.
Pass network
Players drawn at their average position, linked by how often they passed to each other.
PPDA
Passes allowed per defensive action: a common pressing measure. Lower means more aggressive pressing.
Calibration
Whether predicted probabilities match reality: of shots rated 0.2, about 20% should go in.
Brier score and log loss
Ways of scoring probability predictions. Lower is better for both; log loss punishes confident mistakes harder.
Ranked probability score
The standard way to score home, draw and away forecasts, rewarding being close even when wrong.
Elo and Dixon-Coles
Two classic ways of rating teams from results. Elo updates after each match; Dixon-Coles models goals scored as Poisson with a tweak for low scores.
Plan written in October 2026. Data-source terms, free tiers and pricing change, so recheck each source before you launch. Remember StatsBomb attribution on anything you publish with their data.
